# AI 测试用例编写规范

> 版本：2.5
> 文件命名说明：母版文件名为《测试用例编写模板》，具化到项目后为《测试用例编写规范》（存放于 `ai-rules/测试用例编写规范.md`）；各规范文档中的互引《测试用例编写规范》均指具化后的项目版本。
> 适用对象：AI 编程助手、开发者、代码审查者
> 适用项目：Spring Boot / Java / JUnit 5 / Mockito / AssertJ / MockMvc / Testcontainers
> 规范级别：`MUST` 必须；`MUST NOT` 禁止；`SHOULD` 应当；`MAY` 可以

本文档将测试要求写成 AI 可以直接执行、检查和报告的规则。AI 执行任何开发任务时，必须先读取本规范，再根据具体项目的测试目录、构建文件和既有测试风格进行适配。

## 0. 来源与适用边界

本规范从以下项目提炼而来：

- [spring-tdd-zhihu](https://github.com/qianhuihuiji/spring-tdd-zhihu)：完整的仿知乎 TDD 项目实践。
- [build-zhihu-with-springboot-and-tdd-manual](https://github.com/qianhuihuiji/build-zhihu-with-springboot-and-tdd-manual)：TDD 步骤和测试方法手册。

项目已有约定优先于本规范。AI MUST 遵守《AI 辅助开发安全规范》，不得在测试中使用真实密钥、令牌或未脱敏的用户数据。

AI MUST 先检查：

1. `pom.xml`、`build.gradle` 或其他构建文件。
2. CI 配置和测试脚本。
3. 测试目录结构和测试命名风格。
4. 公共集成测试基类、Factory、Fixture、Seeder 和测试配置。
5. 目标模块已有测试及其运行命令。

## 1. AI 执行协议

### 1.1 标准输入

AI 开始工作前，必须明确以下信息：

```yaml
task:
  type: feature | bugfix | behavior_change | refactor | documentation
  description: "用户需求或缺陷描述"
  target_module: "目标模块"
  constraints: []
project:
  test_framework: "JUnit 5"
  build_command: "由 Harness「工具」清单确定"
  test_directories: []
  test_base_classes: []
  test_data_factories: []
```

如果信息无法从项目中发现，AI MUST 在报告中标记为 `UNKNOWN`，不得凭 README 或个人经验假定命令有效。

### 1.2 开始修改前的输出

AI MUST 先输出测试方案（结构见 §13 AI 测试方案模板），等待开发者明确批准后，才能新增或修改测试代码。

**逐个生成（MUST）：** 生成测试用例时，AI MUST 一次只生成一个测试用例，开发者审核确认后，再继续生成下一个；不得一次性批量生成多个用例等待统一审阅。`test_cases` 每次只填写当前这一个用例。已获批准的测试用例视为不可变契约（见 §1.3）。

以下表达才算明确批准：

- “同意该用例。”
- “按该用例编写测试。”
- “同意修改 `<测试文件>`。”

仅提出功能需求、要求修复缺陷或要求遵守 TDD，不等同于批准具体测试用例。

既有测试的任何变更（修改、重写、删除、参数调整）MUST 同样经开发者人工审核确认后才能落地（见 R-014）；AI MUST NOT 以"让测试通过"为由自行变更。

开发者回复模糊（如"看起来没问题"、"可以开始写了"、"go ahead"等）时，AI MUST 追问："是否批准以上测试方案？请确认后我将开始编写测试代码。" 不得自行将模糊回复判定为批准。

### 1.3 修改权限门禁

在测试方案获批前，AI：

- MAY 阅读和分析现有测试。
- MAY 运行现有测试建立基线。
- MAY 展示测试代码草案，但 MUST NOT 写入测试文件。
- MUST NOT 修改、删除、重命名、跳过或禁用测试。
- MUST NOT 先修改生产代码以绕过测试门禁。

获批测试在当前 Red–Green 循环中视为不可变契约。AI MUST NOT 为了让测试通过而擅自改变输入、断言、Fixture、超时、标签或执行条件。

## 2. 核心规则

| ID | 规则 |
|---|---|
| R-001 | AI MUST 先写测试，再写生产代码。 |
| R-002 | 一个测试只验证一个主要业务行为或一个失败主题。 |
| R-003 | 测试名称 MUST 描述业务结果，不得只描述方法名。 |
| R-004 | 测试 MUST 使用 Given–When–Then 结构。 |
| R-005 | 测试 MUST 验证具体业务结果，不得只断言“不为空”或 HTTP 成功。 |
| R-006 | 写操作 MUST 验证适用的持久化、消息、邮件或事件副作用。 |
| R-007 | 测试 MUST 可单独、重复、乱序运行。 |
| R-008 | 测试 MUST 不依赖公网、真实时钟、未控制的随机值或其他测试状态。 |
| R-009 | Red MUST 是由目标行为缺失或缺陷复现造成的失败。 |
| R-010 | Green 阶段 MUST 只实现当前测试所需的最小生产代码。 |
| R-011 | Refactor 阶段 MUST 不新增业务行为。 |
| R-012 | AI MUST 记录测试方案、命令、失败原因、通过结果和回归结果。 |
| R-013 | 涉及外部服务的网络调用（第三方 API、Feign、消息队列等）时，MUST 同时覆盖正常成功场景和失败场景：网络错误、接口异常、超时。 |
| R-014 | 任何测试用例的变更（新增、修改、删除、重写）MUST 经开发者人工审核确认后才能落地；AI MUST NOT 自行变更既有测试。 |

## 3. 行为建模格式

每个测试用例必须能表达为：

```text
Given 前置状态
When  用户或系统执行一个主要动作
Then  可观察结果
And   必要的副作用或附加结果
```

推荐的业务句式：

```text
<主体> 在 <条件> 下，可以/不可以 <行为>，并得到 <结果>。
```

### 3.1 场景覆盖决策表

AI MUST 根据本次行为判断以下场景是否适用。适用场景必须有测试或在测试方案中说明“不适用”的原因。

| 场景 | 检查问题 |
|---|---|
| 成功 | 合法输入的返回结果和副作用是什么？ |
| 未认证 | 未登录调用会发生什么？ |
| 无权限 | 已登录用户操作他人资源会发生什么？ |
| 输入错误 | 空值、格式错误、最小值、最大值如何处理？ |
| 状态错误 | 资源不存在、已删除、未发布或状态不允许时如何处理？ |
| 重复操作 | 操作是否幂等？是否产生重复数据？ |
| 并发 | 并发写入是否破坏唯一性、状态或计数？ |
| 外部失败 | 外部服务网络调用失败时如何处理？涉及外部网络调用时 MUST 覆盖网络错误、接口异常、超时三类失败场景 |
| 边界 | 空集合、单条、分页边界、超长文本和特殊字符如何处理？ |

AI 不必机械地覆盖所有场景，但 MUST 覆盖成功路径和本次行为风险最高的失败路径。

## 4. 测试层级决策

```text
纯逻辑、校验、策略、状态转换、单类分支？
  → unit

依赖 Spring 装配、HTTP、数据库、事务、序列化、安全或组件协作？
  → integration

跨进程、跨系统或关键用户旅程无法被低层测试可靠覆盖？
  → 少量 e2e
```

| 层级 | MUST 验证 | MUST 避免 |
|---|---|---|
| `unit` | 返回值、状态、异常、领域事件和复杂分支 | 网络、真实数据库、真实时钟、过度 Mock |
| `integration` | HTTP 协议、Spring 配置、数据库状态、事务、权限和关键副作用 | 用 Mock 假装数据库或框架已经正确工作 |
| `e2e` | 跨系统关键用户旅程 | 用大量 E2E 代替单元和集成测试 |

同一功能 MAY 同时拥有单元测试和集成测试：集成测试描述用户可见行为，单元测试精确覆盖复杂规则。

边界示例：Service 层的 Repository 调用可以 Mock 且核心逻辑是业务规则校验 → `unit`；需要验证 SQL、事务或数据库约束 → `integration`。

### 4.1 测试推进顺序：分层循环，而非瀑布

推荐按"单元测试 → 契约测试 → 集成测试"分层推进。这是分层循环，不是"先写完所有单元测试、再写集成测试"的瀑布安排：

1. **单元测试先行，驱动 TDD 主循环**。Red—Green—Refactor 要求秒级反馈，只有单元测试能支撑这个节奏。每个行为切片先用单元测试定义业务规则、分支和异常边界，在 Mock 隔离外部依赖下验证（见 §8.2）。
2. **契约测试锁定接口契约**。对外部接口和跨模块调用，补充契约测试锁定请求/响应格式与契约约定。
3. **集成测试作为切片级验收与交付证据**。当切片跨组件边界（数据库、缓存、消息队列、HTTP 等）时，该切片单元测试 Green 后立即补充对应的集成测试，优先使用 Testcontainers 等真实依赖验证协作关系（见 §10），并作为回归证据（见 §15）。

关键要求：

- 集成测试**增量累积**：随每个跨边界切片逐个补充，不得全部积压到功能完成后一次性补写，否则跨组件接缝的假设无法及时验证，问题会集中爆雷。
- 单元测试与集成测试**分层、分阶段运行**（如 `*Test` 与 `*IT` 分属不同测试阶段、不同命令），集成测试不得拖慢单元测试的反馈速度。
- 单元测试保证反馈速度，集成测试验证真实协作关系，二者共同构成测试保护；缺一个，另一个的价值都打折扣。

### 4.2 层级与顺序的最终决定权在开发者

- §4.1 的推进顺序是**推荐默认**，不是强制约束。每个切片采用哪些测试层级、以什么顺序推进、是否跳过某一层，**由开发者决定**。
- AI 输出测试方案（见 §1.2、§13）时 MUST 在 `test_sequence` 中声明本次切片的测试层级、顺序及理由，示例：
  - `先单元后契约/集成`：本切片跨数据库边界，单元测试 Green 后按分层顺序补充契约与集成测试
  - `仅单元测试`：本切片为纯业务规则校验，无外部依赖
  - `直接集成测试`：开发者指定，高风险路径优先验证真实协作
- AI MUST 就测试层级与顺序向开发者**二次确认**，不得自行默认、自行决定或"悄悄跳过"某一层级。开发者明确批准后，测试方案视为不可变契约（见 §1.3）。
- 开发者有权调整推荐顺序（如要求高风险切片直接写集成测试，或允许低风险切片仅单元测试），AI SHOULD 遵循，并在测试方案中说明调整后的影响。

## 5. 命名规则

### 5.1 测试类

```text
<业务能力或动作>Test
```

示例：

```text
UserRegisterTest
ViewQuestionsTest
QuestionPolicyTest
```

### 5.2 测试方法

```text
<条件>_<行为>_<预期结果>
```

正确示例：

```java
void guests_can_register_with_valid_credentials()
void guests_can_not_register_with_duplicate_username()

```

禁止：

```java
void testMethod1()
void works()
void successCase()
```

## 6. 测试代码结构

每个测试方法 MUST 按以下顺序组织：

```java
/**
 * 测试逻辑：游客使用合法注册信息调用注册接口；
 * 前置：无；预期：注册成功返回统一成功码，用户与验证码记录正确入库，验证邮件已发送。
 */
@Test
void guests_can_register_with_valid_credentials() throws Exception {
    // given: 只准备当前场景所需数据
    UserRegisterDto request = UserFactory.createUserRegisterDto();

    // when: 只执行一个主要动作
    ResultActions response = mockMvc.perform(post("/auth/register")
            .contentType(MediaType.APPLICATION_JSON)
            .content(objectMapper.writeValueAsString(request)));

    // then: 断言对外结果和必要副作用
    response.andExpect(status().isOk())
            .andExpect(jsonPath("$.code").value(ResultCode.SUCCESS.getCode()));
}
```

> 示例以集成测试（MockMvc）为例；单元测试结构相同，方法上方中文说明与 given/when/then 结构一致。

结构约束：

- `given` 只准备本场景状态。
- `when` 只执行一个主要动作。
- `then` 断言业务结果和必要副作用。
- 测试可以包含多个相关断言，但失败原因必须属于同一主题。
- 不得在测试中复制生产算法，否则测试和生产代码可能共同犯错。
- 每个测试方法上方 MUST 有中文注释说明测试逻辑（场景、前置条件、主要动作、预期结果），注释 MUST 使用中文。
- 方法内 given / when / then 注释 MUST 使用中文。

## 7. 断言规则

### 7.1 API / 集成测试

按适用性至少验证：

1. HTTP 状态码。
2. 统一响应码或错误码。
3. 响应结构。
4. 关键业务字段。
5. 数据库、消息、邮件或事件副作用。

写操作的最小断言集合应类似：

```text
响应成功
AND 数据已正确保存
AND 关键字段符合业务规则
AND 必要的事件/邮件/消息已产生
```

### 7.2 单元测试

- SHOULD 优先断言返回值、状态变化、异常类型或领域事件。
- 异常测试 MUST 验证异常类型；只有异常消息属于稳定契约时才验证消息。
- MUST NOT 测试私有方法或无业务意义的内部调用顺序。
- 只有调用本身属于契约时，才验证调用次数。

### 7.3 脆弱值

- 集合顺序属于契约时验证顺序，否则使用无序断言。
- 时间、随机值和 ID 使用范围、格式或关系断言。
- MUST NOT 依赖当前时间、随机数或数据库自增 ID 的固定值。

### 7.4 断言正确性

- 断言 MUST 能捕获实现错误：测试通过后，将实现中一个关键字符或关键逻辑故意改错，断言应随之变红；若任何实现错误都不会使断言失败，该断言视为无效（LLM 生成的测试断言错误率超过 62%，见 arXiv 2402.13521）
- 断言无效时，AI MUST NOT 自行修改断言（见 §1.3 不可变契约），MUST 标记为"断言无效"并回到开发者说明原因、重新确认后修正

## 8. 测试数据和替身

### 8.1 测试数据

- MUST 使用 Factory、Builder、Fixture 或 Seeder 表达数据意图。
- MUST 提供合理默认值；单个测试只修改与场景有关的字段。
- MUST 明确区分“构造但不持久化”和“构造并持久化”。
- 测试数据 SHOULD 默认唯一。
- 测试 MUST NOT 依赖其他测试创建的数据。

示例：

```java
Question question = QuestionFactory.createPublishedQuestion();
questionMapper.insert(question);
```

### 8.2 Mock / Fake / Stub

- `unit` 测试 SHOULD Mock 被测边界之外的协作者。
- MUST NOT Mock 值对象和简单领域对象。
- MUST NOT 用自制 ORM、HTTP 客户端或框架 Mock 伪装集成测试。
- 外部服务优先使用 Fake、Stub、本地模拟服务或容器。
- 如果测试因重构频繁破坏，应检查是否绑定了实现细节。

## 9. 隔离和清理

AI MUST 检查以下隔离条件：

```yaml
isolation:
  independent: true
  repeatable: true
  order_independent: true
  database_state_isolated: true
  cache_reset: true
  message_state_reset: true
  mail_state_reset: true
  temp_files_cleaned: true
  external_network_required: false
```

实现要求：

- 优先使用事务回滚、独立 schema/数据库或可靠清理。
- 可以复用容器，但 MUST NOT 复用测试业务状态。
- 文件测试使用临时目录，并在测试后清理。
- 不得通过测试排序解决状态污染。
- 默认测试套件不得依赖公网。
- 真实在线测试必须标记为 `online` 等明确标签，并从快速测试中排除。
- 测试密钥不得写入仓库、日志或快照。

## 10. Spring Boot 项目约定

> 本节约定提炼自 [spring-tdd-zhihu](https://github.com/qianhuihuiji/spring-tdd-zhihu) 实践。AI 具化本规范（生成项目专属《测试用例编写规范》）时，MUST 按项目实际逐项核对并向开发者确认：基类名、容器与中间件清单、认证模拟用户与 Bean 名、`@Tag("online")` 约定等（见「项目适配参数」表）。开发者确认后，写入项目版本。

### 10.1 Controller / 集成测试规范

**测试类结构**

- 类名：`<业务能力>Test`（如 `UserRegisterTest`、`CreateQuestionsTest`、`ViewQuestionsTest`）
- 按业务领域分子包：`integration/users/`、`integration/questions/`、`integration/answers/` …
- 继承集成测试基类（见 §10.2）
- 方法名：小写下划线完整场景描述（`guests_can_register_with_valid_credentials`、`guests_may_not_create_questions`）
- 结构：given-when-then 三段式 + AssertJ 断言

**请求发起**

- `@Autowired protected MockMvc mockMvc`（由基类提供），`mockMvc.perform(...)` 发起 HTTP 请求
- POST 请求体：`.contentType(MediaType.APPLICATION_JSON).content(objectMapper.writeValueAsString(dto))`
- GET 路径参数：`get("/questions/{id}", question.getId())`
- 复杂响应解析：`.andReturn().getResponse().getContentAsString()` + `objectMapper.readValue(json, new TypeReference<CommonResult<XxxVo>>() {})` 解决泛型擦除；分页字段断 `PageInfo` 的 total/size

**断言**

- HTTP 状态码（正常 `isOk()`、未认证 `is(401)`）+ 统一响应结构：`jsonPath("$.code")` 断言业务码常量、`jsonPath("$.message")` 断言错误消息
- 写操作 MUST 查询数据库验证副作用（Mapper `selectByExample` + `hasSize` + 字段断言）；密码等敏感字段用 `passwordEncoder.matches()` 验证，不直接比对密文
- 复杂嵌套响应用 VO 对象字段断言，不堆长 jsonPath 链
- `.andDo(print())` 调试输出 MAY 使用，但不得作为断言依据

**认证前提（具化时确认，1、2 选一）：**

1. 项目需要登录认证 → 沿用下方"认证与权限模拟"约定
2. 项目无需认证 → 删除本节认证相关约定；§3.1 场景覆盖决策表中"未认证/无权限"两行标记为不适用并在测试方案中说明，不写认证测试

**认证与权限模拟**

- 已登录场景：`@WithUserDetails(value = "<用户名>", userDetailsServiceBeanName = "<UserDetailsService Bean 名>")`，走真实 UserDetailsService 加载用户
- 未认证场景：不加任何认证注解，直接断言 401
- 用户名和 Bean 名在具化时与开发者确认（见「项目适配参数」表）

**外部依赖隔离**

- 真实外部服务用 `@MockBean` 隔离（如翻译服务），默认行为在 `@BeforeEach` 中用 `when(...).thenReturn(...)` 固定
- 必须访问真实外部网络的测试标记 `@Tag("online")`，默认构建排除（如 `-DexcludedGroups=online`）

**Feign 外部服务（依赖外部项目的场景）**

- 具化时 MUST 确认：外部依赖方式（Feign / 其他 HTTP 客户端 / 消息）、外部服务清单、外部依赖切换机制
- 默认方式（MUST）：controller 测试用 `@MockBean` 隔离 Feign 客户端，`@BeforeEach` 给定标准响应；Mock 只隔离真正的外部依赖，不得 Mock 本项目内部组件
- 外部失败场景（超时、5xx、业务错误码）MUST 有测试：Mock Feign 抛 `FeignException`，断言统一错误响应
- WireMock 与契约测试（Spring Cloud Contract / Pact）为 MAY 可选层，按项目需要引入，不是强制要求
- 联调全量端到端的切换机制，默认使用"Profile 驱动替身"（具化时与开发者确认，1、2、3 选一）：
  1. 沿用"Profile 驱动替身"（默认，具体要求见下方）
  2. 改用 @MockBean + 专门 `*E2eTest` 类（平时排除 `@Tag("e2e")`，联调时 `-Pe2e` 全量运行）
  3. 其他方式（开发者补充说明）

**选项 1（Profile 驱动替身）具体要求：**

- 测试类不写 `@MockBean`，只注入 Feign 接口
- `test-mock` profile：`spring.cloud.openfeign.enabled: false` 禁用全部 Feign 客户端，并用 `@TestConfiguration @Profile("test-mock")` 提供 Stub Bean（`Mockito.mock` 给定标准响应；外部失败测试用 Stub 抛 `FeignException`）
- `test-real` profile：启用真实 Feign，`feign.*.url` 指向联调环境
- 切换仅一条命令（如 `mvn test` 与 `mvn test -Dspring.profiles.active=test-real`），两条命令 MUST 写入本项目 Harness 规范「工具」命令清单
- 前提：Feign 客户端 url MUST 可配置（`@FeignClient(url = "${xxx.url}")`），不得硬编码
- 测试基类 MUST 在启动时打印当前外部依赖模式（mock/real），防止 Mock 静默生效造成全绿假象

**切换机制前提属于项目改造项：**

- 选项 1（Profile 驱动替身）的落地前提（Feign 客户端 url 可配置化、`test-mock`/`test-real` profile 及 Stub 配置）属于项目改造
- AI 具化时发现前提不满足，MUST 将每一项列为"待确认改造项"输出给开发者，MUST NOT 直接修改生产代码（`@FeignClient`、`application.yml` 等，属 §5 权限边界需确认项）
- 开发者确认并完成改造后，AI 才能按本约定生成项目规范

**异步副作用**

- Kafka 等异步处理用 Awaitility：`await().pollInterval(Duration.ofSeconds(1)).atMost(5, SECONDS).untilAsserted(() -> {...})`

**数据准备**

- Factory 链式表达意图：`XxxFactory.of().unverified().make()`；静态方法创建 DTO（如 `UserFactory.createUserRegisterDto()`）
- DataFaker 生成合法随机数据（手机号 `regexify("1[3-9]\\d{9}")`），密码等字段使用固定合法值
- 显式持久化：`mapper.insert(factory.make())`；组合场景用 Seeder（`seeder().aQuestion(userId)`、`seeder().anAnswer(questionId, userId)`）
- 清理：`@BeforeEach` 中调用基类 `cleanUp*()`；保留项目种子数据（如 `cleanUpUsersExceptDefault()` 只删 id > 3）

### 10.2 Testcontainers 基类规范

**Docker 环境前提（具化时确认）：**

- Testcontainers 依赖 Docker 环境。具化时 MUST 与开发者确认项目是否采用 Testcontainers
- 采用（团队具备 Docker 环境）→ 按本小节约定配置基类
- 不采用 → 由开发者从以下选项确认替代方案并写入项目版本，AI MUST NOT 自行选择（1、2、3 选一）：
  1. 集成测试仅在 CI（具备 Docker 的环境）运行，本地跳过或标记 `@Tag("docker")` 默认排除
  2. 使用本地安装的数据库、缓存等基础设施
  3. 使用项目允许的降级方案（如 H2 兼容模式），并 MUST 在测试方案中说明真实性与降级的差异
- 数据库、缓存、消息队列等本地依赖无论 Testcontainers 是否采用，默认仍用真实基础设施（容器或本地服务），不因外部 Feign 用 Mock 而一并 Mock

基类命名：`BaseContainerTest`（项目实际名在具化时与开发者确认）。

**基类生成规则（采用 Testcontainers 时）：**

采用 Testcontainers 时，基类骨架由 Harness 具化时按项目组件依赖自动生成（生成流程见《AI-Agent-Harness-模板》§0.1「Testcontainers 决策点」），写入 `src/test/java/<包>/BaseContainerTest.java`。

**生成前 MUST 先检查项目是否已有测试基类**（搜索 `*BaseContainerTest*`、`*AbstractTest*`、`*TestBase*`，与 Harness §0.1 探测结果一致）：

- 已存在基类 → 复用现有基类，MUST NOT 覆盖或重复生成；对比现有基类与下方组件映射表，组件依赖或属性注册不一致时输出更新建议，经开发者确认后再更新
- 不存在基类 → 按下方「组件依赖 → 容器段映射表」和「生成步骤」生成新骨架

**组件依赖 → 容器段映射表**（从 `pom.xml` / `build.gradle` 读取依赖，命中组件保留对应段，未命中删除）：

| 项目依赖 | 容器段 | 动态属性注册 |
|---------|--------|-------------|
| `org.testcontainers:mysql` | MySQL | `spring.datasource.url/username/password` |
| `org.testcontainers:postgresql` | PostgreSQL | `spring.datasource.url/username/password` |
| `rocketmq-spring-boot-starter` 或 `rocketmq-client` | RocketMQ（GenericContainer，官方镜像） | `rocketmq.name-server` |
| `spring-kafka` | Kafka | `spring.kafka.bootstrap-servers` |
| `spring-boot-starter-amqp` / `spring-amqp` | RabbitMQ | `spring.rabbitmq.host/port/username/password` |
| `com.redis:testcontainers-redis` | Redis | `spring.data.redis.host/port` |

- 数据库名、用户、密码：优先从 `application.yml` 的 `spring.datasource.*` 读取；读取不到时保留占位并列为 `[需人工确认]`
- 镜像版本：默认 `mysql:8.0`、`redis:7.2.3`、`apache/rocketmq:5.1.0`、`confluentinc/cp-kafka:7.6.1`、`rabbitmq:3.13`，优先取项目实际验证过的版本
- 容器镜像无法直接跑通（启动细节、内存参数、客户端与 broker 版本不兼容等）→ MUST 列为 `[需人工确认]` 改造项，AI 不得自行绕过

**生成步骤（AI 执行）：**

1. 搜索 `@SpringBootApplication` 主类 → 填入 `{{APPLICATION_CLASS}}`；其所在包 → `{{BASE_PACKAGE}}`
2. 检查项目是否已有测试基类（见上文「生成前检查」）
3. 按映射表读取项目依赖 → 确定命中组件段（未命中段及其 import 全部删除）
4. 从 `application.yml` 读取数据库名/用户/密码；读不到保留占位并标注 `[需人工确认]`
5. 渲染下方骨架，写入 `src/test/java/<包>/BaseContainerTest.java`
6. 生成结果记入 Harness 具化变更记录（附录 B），由开发者确认

**结构与注解（参考实现）**

> 说明：以下为 spring-tdd-zhihu 项目的参考实现（MySQL + Kafka + Redis 三组件），实际基类按上方骨架按组件依赖生成，不是直接复制的模板。

```java
@SpringBootTest(classes = XxxApplication.class)
@AutoConfigureMockMvc
public abstract class BaseContainerTest {
    // 容器为 static 字段：所有测试类 JVM 级共享
    public static final MySQLContainer<?> mysql = new MySQLContainer<>("mysql:8.0")
            .withDatabaseName("xxx").withUsername("root").withPassword("root").withReuse(true);
    public static final KafkaContainer kafka = new KafkaContainer(
            DockerImageName.parse("confluentinc/cp-kafka:7.6.1")).withReuse(true);
    public static final RedisContainer redis = new RedisContainer(
            DockerImageName.parse("redis:7.2.3")).withExposedPorts(6379).withReuse(true);

    static {
        // 开启容器复用，static 块启动容器（端口提前分配）
        TestcontainersConfiguration.getInstance().updateUserConfig("testcontainers.reuse.enable", "true");
        mysql.start(); kafka.start(); redis.start();
    }

    @DynamicPropertySource
    static void properties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", mysql::getJdbcUrl);
        registry.add("spring.kafka.bootstrap-servers", kafka::getBootstrapServers);
        registry.add("spring.data.redis.host", redis::getHost);
        registry.add("spring.data.redis.port", redis::getFirstMappedPort);
    }
}
```

要点：

- `@SpringBootTest(classes = 应用主类.class)` + `@AutoConfigureMockMvc` 启动完整上下文
- 容器 MUST 声明为 `static` 字段并在 `static` 块启动：所有测试类共享、端口提前分配、只启动一次
- `.withReuse(true)` + `testcontainers.reuse.enable=true` 开启容器复用，缓解集成测试启动慢
- `@DynamicPropertySource` MUST 用容器实际地址覆盖 `spring.datasource.*`、`spring.kafka.bootstrap-servers`、`spring.data.redis.*` 等配置
- 基类 SHOULD 提供：`@Autowired protected MockMvc mockMvc`、各 Mapper 注入、`cleanUp*()` 清理方法（`deleteByExample`）、惰性单例 `seeder()`

**依赖清单（具化时与项目实际核对）**

- `org.testcontainers:testcontainers` / `:mysql` / `:kafka`（参考 1.21.4）+ `com.redis:testcontainers-redis`
- `org.springframework.security:spring-security-test`（`@WithUserDetails`，仅需认证的项目需要）+ `net.datafaker:datafaker`

**运行方式**

- 参考项目未分离集成阶段：集成/单元测试同一阶段运行（`mvn test`），用 `@Tag("online")` 排除真实外部依赖测试，容器启动成本用 withReuse 摊薄
- AI 具化时 SHOULD 向开发者确认测试运行方式（1、2 选一）：
  1. 沿用"同阶段 + 复用容器"方式（`mvn test` 一次跑完，withReuse 摊薄容器启动成本）
  2. 采用 `*Test`/`*IT` 分离阶段（Surefire / Failsafe）

### 10.3 单元测试

- 使用 `@ExtendWith(MockitoExtension.class)`、`@InjectMocks` 和 `@Mock`。
- 使用 Mockito 隔离 Mapper 和外部服务。
- 使用 AssertJ 表达业务断言。
- 使用 Factory 构造领域对象，降低测试初始化噪声。
- 单元测试 MUST NOT 依赖测试基类：每个测试类自包含（`@ExtendWith(MockitoExtension.class)` + `@Mock`/`@InjectMocks` 已足够）。测试基类仅用于共享容器或 Spring 上下文的集成测试（见 §10.2）。

## 11. Red–Green–Refactor 状态机

```text
PLANNED
  └─(开发者批准测试方案)→ APPROVED
       └─(写入测试并运行)→ RED
            └─(确认失败原因有效)→ RED_VALIDATED
                 └─(实现最小代码并运行)→ GREEN
                      └─(结构调整并回归)→ REFACTORED
                           └─(下一个行为)→ PLANNED
```

### 11.1 有效 Red

Red 只有在以下条件全部满足时才有效：

- 失败原因是目标行为缺失或缺陷仍存在。
- 测试执行到了目标断言或预期的编译边界。
- 不是语法错误、夹具错误、环境故障、网络故障或无关失败。
- 正确实现后预期会通过。
- 断言能捕获实现错误：实现存在单字符或关键逻辑错误时断言会失败（对照检查见 §7.4）；断言对任何实现错误都无感 → 断言无效，Red 不成立，回到开发者重新确认

以下都不是有效 Red：

- Docker、数据库或依赖服务未启动。
- 测试选择器错误导致执行 0 个测试。
- 测试本身空指针或测试数据损坏。
- 与本次任务无关的旧测试失败。
- 测试第一次运行就通过且未完成原因调查。

### 11.2 Green 禁止事项

AI MUST NOT 为了变绿而：

- 删除、跳过、禁用或降低断言。
- 把测试改成只验证“不抛异常”。
- Mock 掉本来需要验证的核心行为。
- 给生产代码加入仅供测试使用的分支。
- 使用无限重试、任意延长超时或固定休眠掩盖竞态。
- 吞掉异常或返回伪造成功结果。
- 顺手修改无关公共接口或大范围重写代码。

## 12. 任务类型协议

### 12.1 新增功能

```text
成功路径
→ 输入校验
→ 身份认证
→ 权限边界
→ 资源状态
→ 重复操作
→ 外部失败/并发
```

### 12.2 修改类任务通用前置：测试审计

以下 12.3—12.5 属于修改类任务（缺陷修复、行为变更、纯重构）。进入这些任务前，AI MUST 先完成测试审计，不得跳过：

1. 列出目标代码已有的测试类路径和用例清单
2. 对照本规范逐一检查：命名是否描述业务行为、是否使用 Given-When-Then、断言是否验证业务结果而非实现细节
3. 输出审计结论，标注符合规范和不符合规范的用例
4. 不符合规范的用例 → MUST 先按本规范重写并确认 Green（重写同样遵守逐个生成规则，见 §1.2）
5. 没有任何测试用例 → MUST 先编写表征测试锁定当前行为并确认 Green
6. 测试用例完备后 → AI MUST 要求开发者人工确认测试逻辑，并提交一次独立 commit（建议格式：`test: 为 <功能> 补充/重写测试用例`）
7. 只有在开发者明确确认测试逻辑并完成提交后，AI 才能进入修改流程。

### 12.3 缺陷修复

缺陷修复属于修改类任务，流程同 12.2（测试审计为强制前置）。额外要求：

```text
测试审计（见 12.2，补齐用例 → 人工确认 → 提交测试基线）
→ 编写回归测试，稳定复现缺陷
→ Red：确认回归测试因为缺陷存在而失败
→ 修复生产代码
→ Green：回归测试通过，原缺陷不再复现
→ 必要时补充根因单元测试
→ 回归：确保修复未引入新问题
```

缺陷修复 MUST 在测试审计阶段确认：既有测试覆盖了缺陷发生路径吗？如果没有 → 先补充、提交、再修复。

### 12.4 行为变更

- 测试审计（见 12.2）→ 确认既有测试符合规范
- MUST 先记录旧行为和新行为
- MUST NOT 直接删除与新需求冲突的旧测试
- 应将测试改写为新的行为契约，并确认旧行为已明确废弃

### 12.5 纯重构

- 测试审计（见 12.2）→ 确认既有测试符合规范
- 如果没有任何测试 → MUST 先编写表征测试锁定当前行为
- 重构前运行现有测试并确认 Green
- 重构后运行相同或更大范围测试
- 报告中应称为”测试保护下的重构”，不应称为完整 Red–Green 循环

## 15. AI 工作证据模板

每个行为切片完成后，AI MUST 输出以下证据；该需求所有切片的证据在需求完成后合并为一条 ai-records 记录（见《AI-Agent-Harness-模板》§6）。

> 记录 MUST NOT 包含密钥、令牌、未脱敏的用户或业务数据（与 §9 隔离要求及《AI 辅助开发安全规范》一致）。

记录级别（完整/精简）由开发者在批准测试方案时一并声明；AI MUST NOT 自行将变更判定为低风险而使用精简模板。精简模板仅含 `behavior` + `red result` + `green result` + `regression result`，其余场景 MUST 使用完整模板。

execution_record:

  approval_summary: ""

    - ""

      - ""
